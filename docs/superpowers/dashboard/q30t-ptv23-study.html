Key results

No training runs launched yet. Acceptance length τ, block size B, and end-to-end rollout throughput at both high and low concurrency land here as milestones report.

Key insights and mistakes

  1. The GPU nodes are the wide CPU hosts, and the data movers are the narrow ones. Routing CPU-only work to cpu_datamover felt like the polite choice, so nobody checked what it costs. A data mover is 96 cores on OCI-HSG and AWS-CMH and 90 on OCI-AGA. Every GB200/GB300 node is 144 Grace cores, and AWS GPU nodes are 140. The counter is CPU-bound, so sending it to a data mover throws away a third of the available width. Staging is the opposite case — it is network-serial at ~1 MB/s and would not use 144 cores if it had them, so it stays on the data mover where it belongs. Route by the resource that is actually scarce, not by the partition’s name. The counter never hardcodes a width: it takes SLURM_CPUS_PER_TASK, then SLURM_CPUS_ON_NODE, so the same sbatch is 90 workers on AGA and 144 on Ptyche without an edit. Whether 144 is worth having is still unmeasured, so the receipt now records bytes, wall time and MB/s per repo — the next run answers “would a wider node help” with a number instead of an argument.
  2. Chained batch beats one long backfill job, and the chain has to be built for it. Ptyche staging was on backfill and Lyris on gb200-backfill, both 8 h and both preemptible. Moved to batch and gb200: non-preemptible, but capped at 5 h. The shorter box is not a downgrade — a 5 h request places into gaps an 8 h request cannot use, which is the same reason the training plan chose chained batch over batch_long. What the shorter box does demand is more rounds: each chain now carries three afterany resume jobs instead of one, because the stager is idempotent and a round that finds everything present costs a tree fetch. scontrol update partition= on a pending job also silently needs timelimit= in the same call — without it Slurm rejects the move as an invalid time limit even when the existing limit fits the new partition.
  3. A job that runs on 96 CPUs is not a job that uses them. The PTV3 row counter was already ProcessPoolExecutor-parallel, so it looked done. It parallelised at shard granularity: six staged shards are between 5 G and 15 G, and each one pinned exactly one worker, so the job’s wall clock was the single largest file no matter how wide the pool. The sbatch then asked for 96 CPUs and passed --workers 48. Plain JSONL above 256 M is now split into byte ranges the pool schedules independently. The correctness rule is one sentence: a record belongs to the chunk holding its first byte. Chunks tile [0, size), so every record is counted exactly once and the total does not depend on scheduling — a chunk skips the record straddling its start and reads past its end to finish the record it owns. Gzip members cannot be entered at an arbitrary offset and parquet is a footer read, so both stay whole-file. Verified against the pre-change reader on a 400 M shard with blank lines and no trailing newline, at every chunk size from 8 M to 128 M, and by a test that sweeps every byte alignment on small fixtures. “It uses a thread pool” answers the wrong question; the one that matters is what the slowest single task is.
  4. Ptyche’s staging job hit its wall clock and took the whole chain down with it, silently. Stage was submitted with --time=02:00:00 against a 5 h partition; at 02:00:18 it went TIMEOUT. The verify job behind it was chained afterok, so it was never going to run — and Slurm removed it from the queue entirely rather than parking it. squeue --me on Ptyche returned nothing, which reads exactly like “finished” if you are scanning five clusters for what is still moving. The watcher printed “done”. Staging is network-serial at roughly 1 MB/s on a single curl, so a 125 G corpus was never going to fit a 2 h box on any cluster. All five chains were rebuilt as stage → afterany resume (8 h) → afterok verify → afterok count, so a timeout resumes instead of deleting the plan. Two node facts fell out of the rebuild: OCI-AGA data-mover nodes have 90 CPUs, not 96, and --cpus-per-task=96 there is a submission error rather than a smaller job — the counter sbatch now asks for --exclusive and sizes its pool from what Slurm reports. Ptyche has no CPU partition at all; its longest is backfill at 8 h. An empty queue is not a completed queue, and afterok makes failure look like absence.
  5. I pointed a job's logs at one directory and its data at another, then validated the wrong one. AWS had two study roots on the same filesystem — /lustre/fsw/…/coreai_dlalgo_modelopt/sna/ and /scratch/fsw/…/nemotron_sw_post/users/sna/, different inodes, same device (/lustre is a symlink to /scratch). Both were growing at the same minute while squeue --me showed a single running job. My first diagnosis — that one root was stale and the verifier was simply aimed at the wrong one — was wrong, and I nearly acted on it. ps -u sna found the second writer: a detached stage_ptv3_v3.sh with PPID 1, running on the login node for 3h44m, invisible to every scheduler query I had made. It held the more advanced tree (8/10 repos) while the Slurm job independently re-downloaded the same corpus into the other root (6/10). A multi-hour download from a login node is also exactly what the MARS conduct rules forbid. Killed the login writer, cancelled the duplicate chain, and resubmitted Slurm against the advanced root so the 109 G already fetched was kept. mtime proves a directory is being written, not by what. When two roots both look live, pair squeue --me with ps -u $USER -o pid,ppid,etime,cmd — a PPID-1 process is a writer no queue listing will ever show.
  6. The eval harness was passing block size where vLLM wants draft length, so the three arms would not have been comparable. run.py forwards --block_size straight into vLLM's num_speculative_tokens, but those are different quantities. DFlash and DFlash2 predict positions 1..B-1 of each block, so K = B - 1; DSpark's Markov head emits the final position too, so K = B. doc/dflash.md settles it without running anything: the default dflash_block_size is 8 and the serving example for that same checkpoint passes num_speculative_tokens: 7. At --block_size 8 the DFlash arms would have proposed 8 tokens from a drafter trained to emit 7, while DSpark correctly got 8 — so the headline acceptance-length comparison would have been measured off by one on two arms out of three. A second bug hid underneath: --block_size defaults to None and run.py always passes the key, so dict.get(key, default) returned None rather than the default and handed vLLM a null horizon whenever the flag was omitted. An arm that runs cleanly and reports a plausible number is the most expensive kind of wrong.
  7. The cluster watcher polled one cluster five times and reported it as five clusters. The script built its host and job tables with declare -A. macOS ships bash 3.2, which has no associative arrays and does not fail on that syntax — it reads [aws]=host as index 0, so each entry overwrote the last and every lookup returned the fifth. The output looked right: five labels, five job lists, all populated. Only the job IDs gave it away, identical across all five columns. A silent fallback that still produces well-shaped output is worse than a crash, and portable shell on a Mac driving Linux clusters is exactly where that bites.
  8. AWS sat idle for 45 minutes because I picked the wrong account, and the scheduler had no way to say so. The staging job held Reason=None with 69 idle nodes and LastSchedEval frozen at submit time — the least informative state Slurm has. I first read that as a queue-depth cutoff and tried raising the QOS from cpu-normal to cpu-short; priority moved from 22,745 to 22,750. Five points. sshare then showed why: FairShare on nemotron_n3_post is 0.127, on nemotron_sw_post 0.915, and PriorityWeightFairShare=100000 against a QOS factor that normalizes against a 108-priority admin QOS and so contributes single digits. Resubmitting on nemotron_sw_post scored 101,502 and started on the spot. Before tuning a knob, measure what the knob is worth — the two levers here differ by four orders of magnitude, and the expensive one was the one I reached for second.
  9. The storage-guard fix broke fourteen tests, and I nearly shipped it believing they were pre-existing. Rewriting the /lustre allow-list into is_durable_path took the suite from 0 to 29 failures. Twelve turned out to be a clean-checkout guard in bundle_manifest.py that refuses to run against a dirty tree — noise from testing uncommitted work. Two were real: tests that assert on the literal guard text, which is the whole point of a test that pins a security-relevant string. The tempting move was to call all fourteen incidental and move on. Stashing the change and re-running gave 118 passed, 0 failed, which settled it in thirty seconds. A regression hypothesis is cheap to falsify and expensive to assume. The replacement tests now execute the predicates against both mount points instead of matching source text, and one new test asserts every script that calls a predicate also defines it — the failure mode of pasting a helper into ten files by hand.
  10. This page claimed five of five clusters were staged. Two of them held nothing at all. Going to look — rather than reading the row I had written — found ptv3_data absent on both AWS-CMH and OCI-AGA, and their job history contains no data-staging job that ever ran. Ptyche and Lyris hold 53 G each and OCI-HSG 97 G, so the real figure was three. The claim was not a lie at the time so much as a number that stopped being re-derived: a dashboard cell is a cached measurement, and nothing invalidates the cache when the world moves. The same discipline already applied to the corpus — read completeness from the pin, not from the process that was supposed to satisfy it — and it applies to this page’s own summary of that work one level up. Any cell that asserts cluster state now has to be cheap to re-derive, and re-derived before it is repeated.
  11. The guard that kept staged data off the wrong storage would have rejected the right storage on two clusters. Both staging jobs asserted STUDY_ROOT == /lustre/*. True on OCI-HSG, Ptyche and Lyris; false on AWS-CMH and OCI-AGA, which mount Lustre at /scratch/fsw. The check would not have misplaced any data — it would have refused to run at all, on exactly the two clusters that had nothing staged, which is a plausible contributor to why they had nothing staged. An allow-list encodes the one environment its author could see. Rewritten to name the places staged data must not go (/home, /raid, /tmp, /cm, /dev/shm), which is what the MARS storage guidance actually says and which does not need updating when a sixth cluster mounts Lustre somewhere new. Write the constraint you mean, not the one instance of it in front of you.
  12. Ptyche and Lyris expose byte-identical staged corpora at byte-identical paths, and they are not the same filesystem. Both show /lustre/fsw/coreai_dlalgo_llm/users/sna/specdec_ptv23 at 53 G with the same status file — the signature of a shared mount, which would have meant one copy masquerading as two and one cluster silently losing its data if the other cleaned up. A marker file written on Ptyche was not visible on Lyris, so they are genuinely independent copies that agree because they were built from the same pinned manifest. Identical content at an identical path is a hypothesis about storage, not evidence of it, and the one-line write-then-read test settles it in seconds.
  13. All three defects a reviewer found in the staging tools shared one shape: each would have produced a wrong number that looked right. The revision tree was fetched unpaginated, so a repository large enough to paginate would have had its later pages silently dropped and then read COMPLETE against the truncated list it did fetch. A file whose size the API omits collapsed to 0, which compares equal to nothing and disabled truncation detection for exactly the file it could not describe. And the row counter added one to any shard ending in a blank line — the ordinary result of concatenating shards — which is a reweighting of the corpus blend, not a crash. None of the three had a failure mode that announces itself; all three end in a plausible number. That is the class of defect worth a reviewer, and it is the class least likely to be caught by running the thing and looking at the output. Re-measuring every recorded count under the fixed counter left all six unchanged, so the pagination and blank-line defects were latent: a latent defect found before it fires is the good outcome, and saying so plainly is more useful than dressing it up as a near miss. Worth recording that the largest repository we have — 259 tree entries — still does not paginate, so the ceiling has not been met, only raised.
  14. My first version of the completeness check marked all ten repositories INCOMPLETE, and a check that always fires is a check nobody reads. The new “any file on disk the revision does not list” rule fired on .tree.json and .errors — the stager’s own bookkeeping, written inside each repo directory and belonging to no revision. Had I shipped it, the honest signal it was built to carry would have been buried under a failure that means nothing, and the fastest way to make the noise stop is to stop looking. The fix distinguishes what the check is actually for: a file the row counter would glob and count as data is a stray and fails the repo, because it contributes rows no revision vouches for; anything else unlisted is reported and does not fail. Aim a check at the consequence, not at the anomaly.
  15. Slurm said Reason=None for half an hour; two throwaway 1-minute jobs said Reason=Priority and named the blockage. The AWS image job sat pending past the 30-minute cancel threshold with no stated reason, which is not the same as no reason existing. Two probe jobs submitted purely to be told why they were queued came back Priority immediately, and the filtered queue showed the cause: 44 jobs from one user at priority 63,232 against my 22,745, all held (Dependency) at the head. A dependency-held queue head does not drain, so nothing behind it schedules except by backfill — and backfill needs a job that fits in a gap. Walltime is a scheduling input, not just a limit. The 2-hour request was a poor backfill candidate for work that takes minutes; resubmitted at 25 minutes it becomes placeable. Two lessons that generalise past this cluster: when the scheduler will not say why, ask it a cheaper question — a disposable probe job is an interrogation tool, not just a test — and request the time the job needs, because an inflated walltime is paid for in queue position.
  16. Ptyche and Lyris declare no GPUs to Slurm at all, so every GPU flag is a submission error there. GRES=(null) on both: jobs take whole nodes and --gpus-per-node=4 is rejected outright with Invalid generic resource (gres) specification. The opposite of AWS-CMH-03, where batch enforces a QOS minimum of 4 GPUs and a CPU-shaped job is refused. So the same submission cannot be portable: the GPU flag must be present on AWS and OCI and absent on Ptyche and Lyris, which is why this belongs in the per-cluster profile rather than a shared template. Both also warn that job names must read <account>-<subproject>.<details> — a warning, not an error, so it is easy to ignore until someone asks whose job is filling the queue.
  17. sbatch runs a copy of your script, so resolving a sibling file from BASH_SOURCE can never work. The row-count job located its Python counter as “the file next to me” — correct under bash, wrong under Slurm, which stages the batch script into a per-job spool directory. At run time the script’s own directory was /cm/local/apps/slurm/var/spool/job6674014 and the counter was not in it. The job failed in 7 seconds, which is the good case: it failed on a guard that checked the file was readable rather than invoking a missing path and letting Python produce something confusing. SLURM_SUBMIT_DIR is the directory the job was submitted from and is what should be searched, with the BASH_SOURCE probe kept last so the script still runs directly outside Slurm. Under a scheduler, a script does not know where it lives.
  18. I left an unbounded find /lustre running for 50 minutes on the Lyris login node — the exact practice the MARS conduct doc names. The doc is explicit: scope searches to your own directory, never leave scans running, and it cites an unbounded find that ran 20–29 hours from a login node. I wrote that rule into the spec and then violated it, on the one cluster whose project is already over its inode quota, hammering the metadata server it can least afford. A second stale walk had been going 2 h 58 m on OCI-HSG. Both killed; all five clusters now show zero. Two lessons. A probe needs a bound at the moment it is written — -maxdepth is not a bound if the root is /lustre, and the fix is to name the directory, as the working query later did. And a background command outlives the question that prompted it: these kept running long after their answers stopped mattering, invisible because nothing reports a process you have forgotten. Sweeping for my own strays is now part of checking on the clusters. Other users’ scans were visible in the same listing, one of them 23 h 43 m old — the pathology is common, which is why the rule exists.
  19. A fix that is committed is not a fix that is deployed. The AWS image job failed twice with the identical Could not resolve proxy error — the second time after the proxy guard was written, reviewed and committed. The job had been queued before the fix existed, and Slurm ran the copy sitting in the cluster home directory, which the commit never touched. Two clusters, two copies of every script, and only one of them is the one that executes. Check the version on the cluster, not the version in the repo — and re-deploy before resubmitting anything that a fix was supposed to repair. The pending job also needed resubmitting outright: a queued job is a snapshot of a command, not a promise to run current code. It then happened again within the hour — I extended the row counter to take its repo list from the environment, and submitted against an OCI-HSG copy deployed minutes before that change. It would have run, succeeded, and quietly counted five repos instead of six, leaving SWE-v1 unmeasured while looking like a clean result. Caught only because this entry had just been written and the check was still in mind: grep -c REPOS on the cluster copy returned 0. Writing the lesson down is what caught the repeat; a fix does not stick from having been understood once.
  20. The counter written to stop a silent zero returned a silent zero, on the two largest repositories in the corpus. The split is clean and was invisible: the repos the datasets-server converted are stored as parquet, the ones it skipped ship JSONL. A JSONL-only counter therefore reports SFT-Math-v4 (545,431 rows) and SFT-SWE-v3 (237,970) as zero rows from zero shards — and its self-validation passed, because both validators it had been given happened to be JSONL. A self-check only covers the cases it samples. The fix is not just parquet support: a repo yielding no recognised shard is now an error, not a zero, because an unhandled layout and an empty dataset are indistinguishable in the output and only one of them is true. Same failure as the datasets-server reporting num_rows: 0 for an unconverted repo, one layer down.
  21. The pinned vLLM image has no pyarrow, and sbatch on AWS does not take container flags. Two small facts that cost a job each. sbatch --container-image=... is rejected outright as an unrecognised option — the pyxis flags are accepted only on srun, so the container has to be entered inside the job script rather than requested by the batch submission. And pyarrow is not a core vLLM dependency, so the runtime image cannot read a parquet footer; the counter gets an arrow reader from an ephemeral venv in /raid/scratch/$SLURM_JOB_ID, node-local and discarded on exit, rather than from a shared install on Lustre.
  22. The stager’s own status file said a repo was staged when 5,901 bytes of it were on disk. A restarted stager truncates its status file and re-walks the manifest, skipping files that already exist — so the sizes it records drift from disk (RL-Math-v2 logged size=52K against 6.9 M actual). Worse, du counts in-flight .part files, which is how SWE-v1 came to be recorded as 11.1 G staged when the pinned revision’s single large shard had not landed at all. Comparing against the revision tree instead — every file the pinned SHA lists, present at its published size — shows five repos complete and byte-exact and SWE-v1 still downloading. A progress log is a claim by the thing being measured. The corpus is the one variable this study controls, so its completeness has to be read from the pin, not from the process that was supposed to satisfy it.
  23. The same image import succeeded on one node and failed on its neighbour, and the working diagnostic was the one that lied. cpu-dm-0004 imported v0.28.0 cleanly; cpu-dm-0007 died on six curl retries against an unresolvable container-cache-node-01. The registry cache is set per node and is not uniform across the partition. What made it confusing is that the script’s own upstream-digest check — Python urllib — passed on the failing node moments earlier: curl honours all_proxy for every scheme and urllib does not map it to HTTPS, so the two tools disagreed about whether the registry was reachable. The cache is a pull-through, not an authorisation gateway, so the fix is to prefer it when its host resolves and import direct when it does not, rather than to retry until the scheduler hands out a good node.
  24. A storage figure was off by a factor of a thousand and had ruled out the best cluster in the study. The spec recorded AWS-CMH-03 at “8.8 T free, 97 percent of capacity” and concluded it could not absorb a checkpoint stream. It is 8.8 P free at 51 percent used — 18 P total, confirmed by both df and lfs df. The unit error and the inverted utilisation claim together demoted the site with the highest FairShare to “corpus only”. A capacity number that excludes an option deserves the same re-measurement as one that selects it, because the cost of a wrong exclusion is invisible — nothing fails, you just never use the thing.
  25. --segment does not appear in sbatch --help on AWS, and is honoured anyway. Grepping the help text says the flag is unsupported; submitting with --segment=16 placed all sixteen nodes on nvl72d136-T[01-16], one NVL72 domain. Help text is documentation, not the parser. The same probe found the opposite asymmetry on the GPU flag: AWS rejects a batch job that omits --gpus-per-node (“Cannot find GPU specification”) while Ptyche and Lyris reject one that includes it — so explicit_gpu_flag is per-cluster and a copied profile fails at submission.
  26. A delegated research result sent us to a prunable nightly when a stable release already had the feature. The subagent reported that vLLM v0.28.0 could not contain vllm#52816, reasoning from merge-base ancestry: the release branched at 53e211d2 four days before the merge, git compare saying “behind 204”. The conclusion was wrong — release branches take cherry-picks after the cut, so ancestry from the branch point proves nothing about tag contents. One request settled it: qwen3_dflash2.py returns HTTP 200 at v0.28.0, 290 lines, with the registry entry and dispatch intact. Ask what a tag contains, not where its branch started. The cost of not checking would have been a nightly pin with a ten-day retention clock instead of a stable release with none.
  27. There is no method: "dflash2" in vLLM, and asking for one fails at config validation. DFlash2 is served as method: "dflash"; the V2 speculator is selected because the draft checkpoint's architectures contains DFlash2DraftModel. That makes the export architecture name load-bearing: a DFlash2 drafter exported under the wrong name serves silently as plain DFlash and would be measured as a duplicate of the DFlash arm rather than failing loudly. The spec's harness plan assumed a symmetric “add two method strings” change and was corrected.
  28. The third arm could never have been submitted — the runner had no dflash2 branch. run_drafter_training.sbatch dispatches on ${METHOD}:${BLOCK_SIZE} and handled dflash and dspark only; dflash2 fell through to the catch-all and exited 2. The horizon table, the manifest, and the tests all already knew about DFlash2, which is exactly why the gap survived — every layer that was easy to check was correct. The new tests execute the case block under bash instead of asserting on its source text, so a future arm cannot be half-added again.
  29. On OCI-HSG the tokens were world-readable the moment they were set: home 755, .bashrc 644. Every user on that cluster could cat /home/sna/.bashrc. This is strictly worse than the argv leak it would have replaced — argv is transient, a dotfile is permanent. The other four clusters were already 700. Setting a secret is two steps, not one: put it somewhere, then check who else can read there.
  30. Ptyche and Lyris had both tokens set and both invisible to every non-interactive shell. Debian's stock .bashrc opens with case $- in *i*) ;; *) return;; esac at line 10; the exports were appended at line 134. Interactive logins saw them, ssh host 'cmd' and every sbatch script did not. Verify a credential the way the job will consume it — ssh host 'echo ${#VAR}', not by logging in and looking.
  31. The corpus is 124.8 G, not the ~70 G the spec claimed. Open-SWE-Traces alone is 46.5 G, a third of the total and larger than the entire estimate's error bar. The spec concluded five per-cluster copies were "effectively free" from the wrong number. Measured per repo: Math-v4 5.5, RL-Math-v2 0.0, SWE-v3 11.7, SWE-v3.5 0.3, SWE-v2 18.1, SWE-v1 11.1, Open-SWE-Traces 46.5, Agentic-v1 5.8, SFT-Agentic-v2 21.9, RL-Lightning-Blend 3.9 G.
  32. The staging script put a live Hugging Face token in curl's argv on five shared login nodes, and its own header claimed it was safe. The comment read "token arrives on stdin and is never written to disk" — true about disk, and irrelevant. /proc on these nodes carries no hidepid, so every user reads every other user's command line; from one login node I could see 2,620 other users' processes in full. Secrets belong in the environment (/proc/PID/environ is owner-only) or on a pipe (curl -K -), never in argv. Two follow-on traps: pkill -f stage_ptv3.sh does not match the child curl that actually holds the token, and pkill -f "Authorization: Bearer" matches its own ssh command line and kills the session — use "Authorization: [B]earer".
  33. The repository already had a staging tool with sha256 verification, and I wrote a shell script instead. examples/dataset/stage_ptv23_sources.py is 741 lines of pinned-revision, atomically-staged, checksum-verified download. The ad-hoc replacement had no integrity check at all and treated any non-empty file as complete, so a truncated shard from an interrupted run would have been counted done forever. This is the second time in this study that not reading the tree first cost real work.
  34. sbatch --test-only answers "can I, and when" for free — and it overturned the plan. The design assumed batch only, with 4 h chunks chained by --dependency=afterany, because batch_long was believed to need approval. --test-only passes on batch_long on all three OCI/AWS clusters, and the 7-day partition reports a sooner estimated start on every one of them. The plan still goes back to chained batch. --test-only answers "is this admissible, and when would this one job start" — not "which strategy finishes first." Short chunks backfill into gaps a 7-day reservation can never use, so the estimate for a single long job is not the throughput of the campaign. A free probe is worth running; it just does not measure what the decision turns on.
  35. Lyris and Ptyche allocate whole nodes and expose no GPU gres, so GPU flags are rejected outright. Gres=(null) on both. --gpus-per-node=4 and --gres=gpu:4 both fail with "Invalid generic resource specification"; you ask for -N and get the whole node. OCI-AGA, OCI-HSG and AWS-CMH-03 do have gpu:4, and on both OCI-AGA and AWS the QOS enforces a 4-GPU minimum (QOSMinGRES) — asking for one GPU is rejected just as firmly as asking for none, so on those clusters there is no such thing as a small GPU job. One submission script cannot serve both families.
  36. GB300 is invisible to the scheduler on every attribute except the node name. On Lyris, where the partitions are labelled, a GB200 node (lyris0001) and a GB300 node (theia0001) report identical RealMemory=940000, identical CPUTot=144, and Gres=(null) on both. Only the hostname prefix and rack features differ. On the unlabelled clusters HBM is readable only from inside a GPU job.
  37. du -sh on Lustre under-reports a directory still being written, and it nearly cost a false corruption alarm. The same four-file repo reported 10 K, 52 K, 6.1 M and 6.6 M across four clusters. Listing the files showed all four shards byte-identical everywhere. Verify a staged corpus by per-file size, never by directory total.
  38. A permission denial on one subdirectory is not evidence about the tree. Tested only <project>/users on AWS-CMH-03 and OCI-AGA, found it root-owned, and wrote a spec section declaring the study GB200-only. The project root itself is group-writable on both. Walk up one level before concluding. Cost: one wrong spec section and a discarded hardware plan.
  39. A bounded search proves nothing about what lies outside its bound. A find -maxdepth 4 scoped to my own directory could not reach a depth-6 path under another user's, and the absence of hits was reported as "no staged corpus exists anywhere." It existed, 42 G of it. State the scope of a negative result alongside the result.
  40. Unbounded find on shared Lustre from a login node is prohibited, and I ran one. MARS records an unbounded scan that ran 20–29 hours and degraded the filesystem for everyone. Scope every scan to your own directory; never leave one running.
  41. A revoked token and a gating denial look nothing alike — check whoami, not the artifact. Lyris and Ptyche appeared to lack a token. They had one; it was fully revoked (401 on whoami, not just on the gated dataset). Fingerprint tokens with sha256 and test the identity endpoint before assuming an environment problem.
  42. DFlash attention was running an Ampere sm80 kernel on Blackwell at roughly 2.5 % of peak. A materialized [B,1,Q,KV] additive mask disqualifies every fused backend, so PyTorch silently fell through to the cutlass memory-efficient path, whose only kernel is sm80. That single backward kernel was 59 % of the step. Silent backend fallback is the most expensive kind of correct-but-slow.
  43. A wrong EAGLE_CAPTURE_IDS final layer id silently caps acceptance length. Capturing the second-to-last hidden instead of the true final one trains without error and just produces a worse drafter. There is no failure signal, so the id has to be derived (build_target_layer_ids(n_layers, n_draft) + 1, plus the true final) rather than guessed.
  44. Trainer memory is set by the loss tensor, not by sequence length. [N, vocab] with N = per_device_batch × num_anchors × block_size dominates, and is independent of training_seq_len. All three arms are held at num_anchors × block_size = 4096 so memory is comparable across them.
  45. The three arms do not share a draft length. DFlash and DFlash2 give K = B − 1; DSpark gives K = B, because its shift-label alignment does not exclude position 0. Comparing arms at equal B but reporting a single K would misattribute the difference. NUM_SPEC_TOKENS is an independent serving knob bounded above by K.
  46. Inodes, not capacity, are the binding storage constraint. Every cluster has hundreds of terabytes free; Lyris is at 93.4 % of its soft inode limit. Checkpoint and shard layout has to favour few large files over many small ones, and the quota that matters is the one nobody checks.
  47. Idle GPUs can get the job killed by the scheduler. In the producer-consumer topology (vLLM serve nodes plus DDP trainer nodes), a stalled serve leaves trainer GPUs idle and risks auto-termination of a 16-node job. Node counts must be sized so both halves stay busy.
  48. DFlash2 is served as method: "dflash", so a wrong drafter produces a plausible number instead of an error. vLLM picks the V2 speculator from the draft checkpoint's architectures (DFlash2DraftModel), not from the method string (vllm#52816). A DFLASH2 run pointed at a DFlash checkpoint starts cleanly, benchmarks DFlash, and reports it as DFlash2. Only a pre-flight check on the checkpoint can catch it — hence _assert_draft_architecture.
  49. Check upstream before writing the patch, not after. Wrote and committed a DSPARK branch for specdec_bench, then found PR #2027 had already merged a better one two days earlier (num_speculative_tokens default 7, plus draft_sample_method). Reset the commit and cherry-picked #2027 instead. A one-minute gh pr list would have saved the whole detour.
  50. "Rows = 0" from the datasets-server means unconverted, not empty. Four of the ten pinned PTV3 repos report zero rows and zero bytes — the server has not converted them. Reading that as an empty dataset would have silently dropped the entire agentic domain from the blend. A zero that comes with a zero byte count is a missing measurement, not a measurement of zero. Nemotron-SWE-v1 is the same trap in softer form: 24,875 converted against an estimated 34,772 is a floor, not a total.
  51. A cluster QOS can enforce a minimum allocation, not just a maximum. A 1-GPU probe on OCI-AGA was rejected with QOSMinGRES; 4 GPUs is the floor. Node generation is also invisible from the scheduler — Gres=gpu:4, RealMemory=942080, and the feature list are identical on GB200 and GB300, so HBM can only be read from inside a GPU job.
  52. The dataset index reported rows=0 for four repos, and zero was not a count. Hugging Face's size endpoint answers from its parquet conversion, so a repo the conversion never covered reports num_rows: 0 in exactly the same shape as a genuinely empty one. Four of the ten PTV3 candidates ship raw JSONL and read as empty: SFT-SWE-v2 (18 G staged), Agentic-v1, SFT-Agentic-v2, RL-Lightning-Blend. Taken at face value those four get weight zero, and the corpus quietly loses all of its agentic data — in a study whose entire subject is agentic rollout. Nothing would have failed. The counter that replaces it validates itself against the repos the index does cover and withholds every number if it disagrees, because the failure mode being guarded is a plausible wrong count, not a crash.
  53. The CPU partitions are Grace, not x86 — which is the only reason importing the image there is safe. cpu and cpu_datamover on AWS-CMH-03 report Arch=aarch64, 96 cores, 240 G. That matters more than it sounds: enroot import resolves a multi-arch manifest against the host, so the same command on an x86 mover would have silently staged an x86 image that the Grace compute nodes cannot run, discovered only at the first training launch. The staging job now asserts uname -m before importing and greps the squashfs for /lib/aarch64-linux-gnu after. Free lesson attached: a CPU partition with no GPU floor and no time limit is the right home for image imports and dataset scans on a cluster whose GPU QOS forbids small jobs.
