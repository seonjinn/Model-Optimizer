Key results

No training runs launched yet. Acceptance length τ, block size B, and end-to-end rollout throughput at both high and low concurrency land here as milestones report.

Key insights and mistakes

  1. A storage figure was off by a factor of a thousand and had ruled out the best cluster in the study. The spec recorded AWS-CMH-03 at “8.8 T free, 97 percent of capacity” and concluded it could not absorb a checkpoint stream. It is 8.8 P free at 51 percent used — 18 P total, confirmed by both df and lfs df. The unit error and the inverted utilisation claim together demoted the site with the highest FairShare to “corpus only”. A capacity number that excludes an option deserves the same re-measurement as one that selects it, because the cost of a wrong exclusion is invisible — nothing fails, you just never use the thing.
  2. --segment does not appear in sbatch --help on AWS, and is honoured anyway. Grepping the help text says the flag is unsupported; submitting with --segment=16 placed all sixteen nodes on nvl72d136-T[01-16], one NVL72 domain. Help text is documentation, not the parser. The same probe found the opposite asymmetry on the GPU flag: AWS rejects a batch job that omits --gpus-per-node (“Cannot find GPU specification”) while Ptyche and Lyris reject one that includes it — so explicit_gpu_flag is per-cluster and a copied profile fails at submission.
  3. A delegated research result sent us to a prunable nightly when a stable release already had the feature. The subagent reported that vLLM v0.28.0 could not contain vllm#52816, reasoning from merge-base ancestry: the release branched at 53e211d2 four days before the merge, git compare saying “behind 204”. The conclusion was wrong — release branches take cherry-picks after the cut, so ancestry from the branch point proves nothing about tag contents. One request settled it: qwen3_dflash2.py returns HTTP 200 at v0.28.0, 290 lines, with the registry entry and dispatch intact. Ask what a tag contains, not where its branch started. The cost of not checking would have been a nightly pin with a ten-day retention clock instead of a stable release with none.
  4. There is no method: "dflash2" in vLLM, and asking for one fails at config validation. DFlash2 is served as method: "dflash"; the V2 speculator is selected because the draft checkpoint's architectures contains DFlash2DraftModel. That makes the export architecture name load-bearing: a DFlash2 drafter exported under the wrong name serves silently as plain DFlash and would be measured as a duplicate of the DFlash arm rather than failing loudly. The spec's harness plan assumed a symmetric “add two method strings” change and was corrected.
  5. The third arm could never have been submitted — the runner had no dflash2 branch. run_drafter_training.sbatch dispatches on ${METHOD}:${BLOCK_SIZE} and handled dflash and dspark only; dflash2 fell through to the catch-all and exited 2. The horizon table, the manifest, and the tests all already knew about DFlash2, which is exactly why the gap survived — every layer that was easy to check was correct. The new tests execute the case block under bash instead of asserting on its source text, so a future arm cannot be half-added again.
  6. On OCI-HSG the tokens were world-readable the moment they were set: home 755, .bashrc 644. Every user on that cluster could cat /home/sna/.bashrc. This is strictly worse than the argv leak it would have replaced — argv is transient, a dotfile is permanent. The other four clusters were already 700. Setting a secret is two steps, not one: put it somewhere, then check who else can read there.
  7. Ptyche and Lyris had both tokens set and both invisible to every non-interactive shell. Debian's stock .bashrc opens with case $- in *i*) ;; *) return;; esac at line 10; the exports were appended at line 134. Interactive logins saw them, ssh host 'cmd' and every sbatch script did not. Verify a credential the way the job will consume it — ssh host 'echo ${#VAR}', not by logging in and looking.
  8. The corpus is 124.8 G, not the ~70 G the spec claimed. Open-SWE-Traces alone is 46.5 G, a third of the total and larger than the entire estimate's error bar. The spec concluded five per-cluster copies were "effectively free" from the wrong number. Measured per repo: Math-v4 5.5, RL-Math-v2 0.0, SWE-v3 11.7, SWE-v3.5 0.3, SWE-v2 18.1, SWE-v1 11.1, Open-SWE-Traces 46.5, Agentic-v1 5.8, SFT-Agentic-v2 21.9, RL-Lightning-Blend 3.9 G.
  9. The staging script put a live Hugging Face token in curl's argv on five shared login nodes, and its own header claimed it was safe. The comment read "token arrives on stdin and is never written to disk" — true about disk, and irrelevant. /proc on these nodes carries no hidepid, so every user reads every other user's command line; from one login node I could see 2,620 other users' processes in full. Secrets belong in the environment (/proc/PID/environ is owner-only) or on a pipe (curl -K -), never in argv. Two follow-on traps: pkill -f stage_ptv3.sh does not match the child curl that actually holds the token, and pkill -f "Authorization: Bearer" matches its own ssh command line and kills the session — use "Authorization: [B]earer".
  10. The repository already had a staging tool with sha256 verification, and I wrote a shell script instead. examples/dataset/stage_ptv23_sources.py is 741 lines of pinned-revision, atomically-staged, checksum-verified download. The ad-hoc replacement had no integrity check at all and treated any non-empty file as complete, so a truncated shard from an interrupted run would have been counted done forever. This is the second time in this study that not reading the tree first cost real work.
  11. sbatch --test-only answers "can I, and when" for free — and it overturned the plan. The design assumed batch only, with 4 h chunks chained by --dependency=afterany, because batch_long was believed to need approval. --test-only passes on batch_long on all three OCI/AWS clusters, and the 7-day partition reports a sooner estimated start on every one of them. The plan still goes back to chained batch. --test-only answers "is this admissible, and when would this one job start" — not "which strategy finishes first." Short chunks backfill into gaps a 7-day reservation can never use, so the estimate for a single long job is not the throughput of the campaign. A free probe is worth running; it just does not measure what the decision turns on.
  12. Lyris and Ptyche allocate whole nodes and expose no GPU gres, so GPU flags are rejected outright. Gres=(null) on both. --gpus-per-node=4 and --gres=gpu:4 both fail with "Invalid generic resource specification"; you ask for -N and get the whole node. OCI-AGA, OCI-HSG and AWS-CMH-03 do have gpu:4 and OCI-AGA's QOS enforces a 4-GPU minimum. One submission script cannot serve both families.
  13. GB300 is invisible to the scheduler on every attribute except the node name. On Lyris, where the partitions are labelled, a GB200 node (lyris0001) and a GB300 node (theia0001) report identical RealMemory=940000, identical CPUTot=144, and Gres=(null) on both. Only the hostname prefix and rack features differ. On the unlabelled clusters HBM is readable only from inside a GPU job.
  14. du -sh on Lustre under-reports a directory still being written, and it nearly cost a false corruption alarm. The same four-file repo reported 10 K, 52 K, 6.1 M and 6.6 M across four clusters. Listing the files showed all four shards byte-identical everywhere. Verify a staged corpus by per-file size, never by directory total.
  15. A permission denial on one subdirectory is not evidence about the tree. Tested only <project>/users on AWS-CMH-03 and OCI-AGA, found it root-owned, and wrote a spec section declaring the study GB200-only. The project root itself is group-writable on both. Walk up one level before concluding. Cost: one wrong spec section and a discarded hardware plan.
  16. A bounded search proves nothing about what lies outside its bound. A find -maxdepth 4 scoped to my own directory could not reach a depth-6 path under another user's, and the absence of hits was reported as "no staged corpus exists anywhere." It existed, 42 G of it. State the scope of a negative result alongside the result.
  17. Unbounded find on shared Lustre from a login node is prohibited, and I ran one. MARS records an unbounded scan that ran 20–29 hours and degraded the filesystem for everyone. Scope every scan to your own directory; never leave one running.
  18. A revoked token and a gating denial look nothing alike — check whoami, not the artifact. Lyris and Ptyche appeared to lack a token. They had one; it was fully revoked (401 on whoami, not just on the gated dataset). Fingerprint tokens with sha256 and test the identity endpoint before assuming an environment problem.
  19. DFlash attention was running an Ampere sm80 kernel on Blackwell at roughly 2.5 % of peak. A materialized [B,1,Q,KV] additive mask disqualifies every fused backend, so PyTorch silently fell through to the cutlass memory-efficient path, whose only kernel is sm80. That single backward kernel was 59 % of the step. Silent backend fallback is the most expensive kind of correct-but-slow.
  20. A wrong EAGLE_CAPTURE_IDS final layer id silently caps acceptance length. Capturing the second-to-last hidden instead of the true final one trains without error and just produces a worse drafter. There is no failure signal, so the id has to be derived (build_target_layer_ids(n_layers, n_draft) + 1, plus the true final) rather than guessed.
  21. Trainer memory is set by the loss tensor, not by sequence length. [N, vocab] with N = per_device_batch × num_anchors × block_size dominates, and is independent of training_seq_len. All three arms are held at num_anchors × block_size = 4096 so memory is comparable across them.
  22. The three arms do not share a draft length. DFlash and DFlash2 give K = B − 1; DSpark gives K = B, because its shift-label alignment does not exclude position 0. Comparing arms at equal B but reporting a single K would misattribute the difference. NUM_SPEC_TOKENS is an independent serving knob bounded above by K.
  23. Inodes, not capacity, are the binding storage constraint. Every cluster has hundreds of terabytes free; Lyris is at 93.4 % of its soft inode limit. Checkpoint and shard layout has to favour few large files over many small ones, and the quota that matters is the one nobody checks.
  24. Idle GPUs can get the job killed by the scheduler. In the producer-consumer topology (vLLM serve nodes plus DDP trainer nodes), a stalled serve leaves trainer GPUs idle and risks auto-termination of a 16-node job. Node counts must be sized so both halves stay busy.
  25. DFlash2 is served as method: "dflash", so a wrong drafter produces a plausible number instead of an error. vLLM picks the V2 speculator from the draft checkpoint's architectures (DFlash2DraftModel), not from the method string (vllm#52816). A DFLASH2 run pointed at a DFlash checkpoint starts cleanly, benchmarks DFlash, and reports it as DFlash2. Only a pre-flight check on the checkpoint can catch it — hence _assert_draft_architecture.
  26. Check upstream before writing the patch, not after. Wrote and committed a DSPARK branch for specdec_bench, then found PR #2027 had already merged a better one two days earlier (num_speculative_tokens default 7, plus draft_sample_method). Reset the commit and cherry-picked #2027 instead. A one-minute gh pr list would have saved the whole detour.
  27. "Rows = 0" from the datasets-server means unconverted, not empty. Four of the ten pinned PTV3 repos report zero rows and zero bytes — the server has not converted them. Reading that as an empty dataset would have silently dropped the entire agentic domain from the blend. A zero that comes with a zero byte count is a missing measurement, not a measurement of zero. Nemotron-SWE-v1 is the same trap in softer form: 24,875 converted against an estimated 34,772 is a floor, not a total.
  28. A cluster QOS can enforce a minimum allocation, not just a maximum. A 1-GPU probe on OCI-AGA was rejected with QOSMinGRES; 4 GPUs is the floor. Node generation is also invisible from the scheduler — Gres=gpu:4, RealMemory=942080, and the feature list are identical on GB200 and GB300, so HBM can only be read from inside a GPU job.
