# Q30 Thinking PTV2/PTV3 From-Scratch Drafter Study Design

## Decision

Train DFlash, DSpark, and DFlash2 from fresh drafter initialization on one
target-generated PTV2/PTV3 corpus family for
`Qwen/Qwen3-30B-A3B-Thinking-2507`. The completed PTV2 1.3M DFlash and DSpark
checkpoints remain historical references; they are not initialization inputs
for the new study. "From scratch" applies to the drafter parameters; the exact
pretrained Q30 target remains frozen and supplies target features and labels.

The experiment separates two questions:

1. Does target synthesis and a Math/SWE/agentic PTV2/PTV3 blend improve over
   the historical PTV2 1.3M construction?
2. On the selected corpus, which of DFlash, DSpark, and DFlash2 gives the best
   acceptance and rollout throughput at matched training exposure?

The data study uses DFlash first. Only after the corpus comparison reaches its
primary gate do all three drafter architectures train from scratch on the same
immutable selected corpus. This avoids paying for nine full runs while keeping
the data and architecture effects identifiable.

## Scope

This design covers source eligibility, held-out exclusion, prompt identity,
target-response synthesis, executable agentic trajectories, corpus sizing,
immutable publication, from-scratch training, staged GB200 execution, and
evaluation. It supersedes the earlier assumption that 10,240 rows could
demonstrate domain adaptation.

The existing Q30 700K continuation remains a separate experiment. Its
authenticated parents, source-native continuation data, output roots, and
receipts must not be relabelled as this from-scratch study.

This design does not authorize a push, dataset build, target-generation job,
training job, or cancellation. Those actions remain behind source, held-out,
runtime, scheduler, and user-approval gates.

## Scientific questions and controls

### Historical reference

The existing Q30 Thinking parents were trained on 1,300,000 PTV2 source-row
occurrences:

| Domain | Rows | Share |
|---|---:|---:|
| Chat | 627,720 | 48.2862% |
| Math | 239,467 | 18.4205% |
| Code | 175,000 | 13.4615% |
| German | 257,813 | 19.8318% |
| STEM, SWE, agentic, and tool use | 0 | 0% |
| **Total** | **1,300,000** | **100%** |

The completed DFlash and DSpark checkpoints are evaluated with the new
evaluator bundle as historical references. They cannot be the sole causal
control because the original run did not record an exact cumulative
assistant-loss-token counter and used a different response/training pipeline.

### Corpus ablation

The first stage trains DFlash from scratch on three data constructions under
the same current source commit, target, tokenizer, template, seed, topology,
optimizer, and cumulative assistant-loss-token gates:

- `H-native`: the exact historical 1.3M prompt identities with their
  authenticated source-native responses. This is a reproduction control, not
  a candidate production corpus.
- `H-synth`: the same historical prompt identities with the source assistant
  responses removed and regenerated by the exact target.
- `M-synth`: a new PTV2/PTV3 Math/SWE/agentic mixture whose non-replay
  assistant responses and executable agentic actions are generated by the
  exact target.

`H-native` versus `H-synth` measures the response-generation change.
`H-synth` versus `M-synth` measures the prompt/source blend change. The old
checkpoint versus the new controls remains descriptive rather than causal.
The H controls retain the historical prompt composition and therefore its
natural per-domain token profile. They match `M-synth` on total cumulative
assistant-loss tokens, not on the new per-lane mixture; imposing that mixture
would destroy the prompt-blend control.

### Architecture comparison

After the data report reaches the 1B primary gate, the selected target-synth
corpus trains DFlash, DSpark, and DFlash2 from scratch. All three consume the
same corpus bytes, deterministic sample order, target checkpoint, tokenizer,
chat template, seed, block size, target-layer capture, training topology, and
cumulative assistant-loss-token views.

No new run loads drafter weights, optimizer state, scheduler state, RNG state,
data-loader state, global step, or W&B identity from the historical parents.

## Target and prompt identity

Every production artifact binds the exact target repository, 40-character
revision, model-tree digest, tokenizer-tree digest, chat-template digest,
special-token IDs, reasoning mode, generation policy, and runtime image.

The canonical prompt UUID is computed before target generation. It covers:

- system, developer, and user messages;
- repository/task context;
- top-level tool declarations;
- prior assistant actions only when they are part of an immutable prefix;
- prior tool results and their call IDs;
- source repository, revision, file digest, split, and row index;
- thinking mode and response lane.

It excludes the source assistant answer being regenerated, storage-only
metadata, target output, reward, verifier result, and selection rank. A UUID
collision with different canonical prompt bytes is a hard error.

## Source policy

### PTV2

The physical PTV2 inventory is rooted at the staged OCI-HSG copy associated
with revision `5c89e01dd720ae0f4058445ed49c5fb68a03c76e`. Eligible domains are
Math, Code, STEM, Chat/instruction, and DE/JA/ES/FR/IT multilingual data.

PTV2 source completions are used only by `H-native`. `H-synth` and `M-synth`
strip the response being regenerated. The source license, generator, category,
version, UUID, file digest, and row index remain provenance fields and never
enter the chat text.

### PTV3 and related candidate sources

The source registry may admit only exact-revision, file-hashed entries from
the following families:

- Math/reasoning: Nemotron Math and SFT Math collections, RL Math prompts,
  and licensed OpenInstruct/DAPO-style prompt sets;
- agentless SWE: Nemotron-SFT-SWE-v3 and agentless subsets from prior
  Nemotron SWE releases;
- interactive SWE: Nemotron-SWE-v1, OpenHands/SWE-agent/mini-SWE-agent
  trajectories from Nemotron-SFT-SWE-v2/v3, and reproducible executable task
  environments;
- general tools: Nemotron-Agentic-v1 and schema-compatible
  Nemotron-SFT-Agentic-v2 subsets;
- Code, STEM, instruction following, structured output, and multilingual
  sources from the pinned PTV3 collection.

A repository name alone is not authority. Each admitted source manifest must
record the exact revision, configuration, split, every physical relative path,
file size, SHA-256, row count, row-schema digest, license expression, and
approved-use classification. Adding or changing a source creates a new corpus
policy identity.

## Held-out and contamination policy

Selection excludes the authenticated union of five independently reviewed
catalogs:

- `speed`;
- `math`;
- `code`;
- `swe`;
- `tool`.

The union includes prompt, answer, patch, test, repository/task, and derived
trajectory identities. It covers the exact AIME, GSM8K, MATH, HumanEval,
MBPP, LiveCodeBench, SWE-bench, SPEED-Bench, terminal-agent, and tool-use
variants used by evaluation. Normalized-content and source-native identifiers
are both excluded.

The current conservative held-out v2 design remains state `P`. No corpus
publication or GPU synthesis is admitted until its source acquisition,
semantic review, allowed-signers root, signatures, and replay receipt are
complete.

## Response lanes

### Target-synthesis lane

Math, Code, STEM, instruction, multilingual, and agentless SWE records retain
only prompt-bearing context. The exact Q30 target regenerates the assistant
response under a pinned sampling policy. The receipt records request bytes,
response bytes, target and tokenizer identities, sampling parameters, stop
reason, token counts, server/runtime digests, and retry history.

The source response is neither passed to the target nor used as a label. A
partial, empty, failed, overlength, or non-replayable response is rejected.

### Executable agentic lane

Interactive SWE and general tool records preserve tool schemas and the valid
prefix up to the next assistant action. The exact target generates the action.

- When a reproducible tool or repository environment is available, the target
  action is executed and the newly observed tool result is appended before the
  next target action.
- When only a recorded result is available, that result may be appended only
  if the normalized target call exactly matches the source call in function
  name, canonical arguments, and call cardinality.
- A divergent action without an executable environment rejects the trajectory;
  the builder never attaches an unrelated recorded tool result.

Function arguments are canonicalized from either JSON strings or JSON objects
before validation. Every function must be declared. Call IDs are non-empty and
unique, each result resolves one preceding call, and no unresolved call may
cross the next non-tool message or the end of the trajectory.

### Source-native replay ablation

Complete source-native trajectories may be retained under a separate replay
identity. They preserve reasoning, calls, results, and order, but they are not
reported as target-generated data and do not enter the primary `M-synth`
comparison.

## Domain mixture

`M-synth` and every selected production view use assistant-loss-token quotas,
not row, byte, context-token, or file quotas:

| Lane | Share |
|---|---:|
| Agentless SWE target synthesis | 15% |
| Interactive SWE execution | 10% |
| General agentic/tool execution | 10% |
| Math/reasoning | 25% |
| Code | 15% |
| STEM/science | 15% |
| Instruction/chat | 5% |
| Multilingual | 5% |
| **Total** | **100%** |

Multilingual selection divides its quota equally among DE, JA, ES, FR, and IT
after capacity checks. No source is relabelled into another domain to cover a
shortfall. A short domain blocks that view rather than redistributing quota.

## Corpus cardinality

For `M-synth`, the former 1.3M value is a minimum comparison boundary, not an
upper bound. Its production row count is derived deterministically after
target generation:

1. Build an eligible, held-out-clean prompt inventory per lane.
2. Order each lane by SHA-256 of the corpus policy, seed, lane, source identity,
   source row, and prompt UUID.
3. Generate and validate target responses into an immutable candidate reserve.
4. Merge lane orders with deterministic largest-remainder scheduling.
5. Let `N1` be the smallest merged candidate prefix that contains at least
   1,300,000 unique prompts and enough accepted assistant-loss-token capacity
   in every lane to construct its exact 1B quota.
6. Construct nested 0-to-256M and 256M-to-1B segments per lane. Mask excess
   assistant tokens in each segment's boundary row and do not recycle those
   masked tokens. Merge the lane segments with the same deterministic
   scheduler, so the serialized 256M training schedule is a byte-identical
   prefix of the 1B schedule. Publish both views with `N1`.
7. For scale-up, continue the immutable lane orders. Let `N4` be the smallest
   merged candidate prefix with enough capacity in every lane to construct its
   exact 4B quota. Build its 1B-to-4B segment by the same rule, with the 1B
   training schedule as a byte-identical prefix.

`N1` and `N4` may exceed 1.3M rows without another design change. Their exact
values are outputs of signed capacity and build receipts, not hand-selected
constants. The builder prioritizes new unique prompts. It never pads, cycles,
duplicates, or silently adds epochs to meet a unique-data view. If source or
generation capacity cannot produce a view, it publishes a blocker receipt.
`N1` and `N4` describe immutable candidate reserves. Every report separately
states how many unique rows have actually contributed unmasked assistant-loss
tokens at each checkpoint; reserve rows are never counted as training exposure.

Repeated exposure is allowed only as a separately named scale ablation with an
explicit epoch count and is never described as additional unique corpus data.
If either historical 1.3M control lacks enough unique accepted tokens for a
named token gate, that comparison fails closed at the largest common exact
token boundary and the primary 1B corpus-selection gate remains incomplete; it
is never rescued by silent repetition.

## Training views and gates

### System canary

The system canary contains exactly 10,240 rows and runs exactly 20 optimizer
steps at global batch size 512. Its row allocation is:

| Lane | Rows |
|---|---:|
| Agentless SWE | 1,536 |
| Interactive SWE | 1,024 |
| General agentic/tool | 1,024 |
| Math/reasoning | 2,560 |
| Code | 1,536 |
| STEM/science | 1,536 |
| Instruction/chat | 512 |
| Multilingual | 512 |
| **Total** | **10,240** |

The canary proves schema handling, finite loss, gradients, distributed
activity, target serving, FlexAttention, checkpointing, export, reload, and
evaluation plumbing. It does not prove domain learning, architecture ranking,
or production readiness.

### Historical row-count diagnostic

Each corpus-ablation arm also emits a diagnostic checkpoint after 1,300,000
distinct sample rows have contributed assistant-loss tokens. This is the
closest current-pipeline comparison to the historical 1.3M-row run, but it is
not the primary selection gate because response lengths and therefore token
exposure can differ. The receipt reports its exact assistant-loss tokens and
optimizer steps. It never cycles a shorter corpus to reach the row count.

### Domain pilot

The first `M-synth` scientific view consumes exactly 256,000,000
assistant-loss tokens with these lane quotas:

| Lane | Assistant-loss tokens |
|---|---:|
| Agentless SWE | 38,400,000 |
| Interactive SWE | 25,600,000 |
| General agentic/tool | 25,600,000 |
| Math/reasoning | 64,000,000 |
| Code | 38,400,000 |
| STEM/science | 38,400,000 |
| Instruction/chat | 12,800,000 |
| Multilingual | 12,800,000 |

This gate detects an initial learning signal and retention problems. No corpus
or architecture is eliminated solely from the 256M result. The H controls stop
at the same total token boundary while retaining their natural domain profile.

### Primary gate

The primary `M-synth` comparison consumes exactly 1,000,000,000 cumulative
assistant-loss tokens with these lane quotas:

| Lane | Assistant-loss tokens |
|---|---:|
| Agentless SWE | 150,000,000 |
| Interactive SWE | 100,000,000 |
| General agentic/tool | 100,000,000 |
| Math/reasoning | 250,000,000 |
| Code | 150,000,000 |
| STEM/science | 150,000,000 |
| Instruction/chat | 50,000,000 |
| Multilingual | 50,000,000 |

The data-ablation report at this gate selects the corpus used for the
three-architecture comparison. Selection requires complete paired evaluator
evidence and an independent review; training loss alone cannot select a corpus.
The H controls stop at the same total token boundary while retaining their
natural domain profile.

### Scale-up gate

The optional scale-up consumes exactly 4,000,000,000 cumulative
assistant-loss tokens with the same mixture. It runs only after the 1B report
shows continuing learning and no unresolved retention or target-equivalence
failure. The 4B view uses unique data through `N4`; a repeat-based comparison
has a different experiment identity.

## Training contract

The initial family uses block size 8 and proposes seven draft tokens so it can
be compared with the historical B8 drafters and the currently validated
DFlash2 serving horizon. A block-size-16 study is a later experiment identity.

All three architectures share:

- five draft layers;
- 32 attention heads, four KV heads, head dimension 128, and intermediate size
  6,144;
- Q30 mask token 151669;
- sequence length 4,096;
- target-layer capture `[2,13,24,35,46,48]`;
- fresh drafter model, optimizer, linear scheduler, RNG, output, and W&B
  identities;
- identical target-synth corpus bytes and deterministic sample order;
- the exact 256M, 1B, and optional 4B assistant-token counters;
- FlexAttention enabled with `TRITON_CACHE_DIR` on node-local
  `/raid/scratch`;
- immutable source, target, runtime, dataset, and completion receipts.

DFlash2 uses `projector_type=dflash2`, convolution kernel size 2, convolution
group size 16, selector rank 256, selector top-k 16, and selector-loss weight
1.0. Its dynamic convolution projection is zero-initialized so the convolution
is an actual identity at initialization; a test must compare the shared
backbone numerically without manually mutating the module. The selector remains
fresh and deterministic under the experiment seed.

The source commit must contain the reviewed equivalents of ModelOpt DFlash2 PR
2216, training-speed PR 2279, Qwen3 DSpark example PR 2164, and the merged
same-architecture warm-start support from PR 2149. This from-scratch study
does not set `dflash_init_checkpoint`.

## Distributed execution

Source audit and target generation prefer OCI-HSG because the staged PTV2 copy
is local there. Training may run on OCI-HSG, Ptyche, or Lyris only after that
cluster has an independently approved immutable runtime and passes the same
one-node, two-node, and sixteen-node platform sequence.

The proven Q30 streaming shape uses 16 GB200 nodes, eight target-serving nodes,
eight trainer nodes, four GPUs per node, 32 trainer ranks, and target tensor
parallel size 2. A topology change creates a new performance identity and
cannot be compared as the same throughput run.

Every submission runs Slurm `--test-only`, confirms an exact source commit is
signed and pushed, checks only the user's or exact job's scheduler state, and
monitors a newly running job for five minutes. Execution stages all high-churn
data and caches on node-local `/raid/scratch`; durable corpus, checkpoint, and
bounded evidence artifacts reside on `/lustre`.

## Evaluation

Each run is evaluated at initialization, 256M, 1B, and 4B when present. The
same evaluator source, prompts, target, decoding settings, proposed-token
horizon, concurrency, and GB200 runtime identity are used for every paired
comparison.

Required outputs include:

- acceptance length, acceptance rate, accepted tokens per proposed token, and
  verifier calls per output token;
- generation and end-to-end throughput and latency by domain and concurrency;
- Math trajectories for AIME, MATH, and GSM-style held-outs;
- SWE-bench-derived held-outs with repository and patch contamination removed;
- interactive SWE and general tool trajectory acceptance by turn and call
  type;
- Chat, Code, STEM, and multilingual retention;
- DFlash2 selector accuracy and coverage;
- exact target-output equivalence under deterministic decoding;
- checkpoint/export reload and serving evidence.

The report shows confidence intervals from paired prompts and separates unique
corpus tokens, cumulative training exposure, epochs, rows, and optimizer steps.
It does not infer scientific improvement from loss, a 20-step canary, or an
unpaired throughput number.

## Immutable artifacts and receipts

Each source inventory, prompt selection, generation result, corpus view,
training run, checkpoint, export, and evaluation has a canonical JSON manifest
and content digest. Publication writes to a job-unique partial directory,
rehashes every file, fsyncs files and directories, and atomically renames into
a previously absent immutable namespace.

The final corpus receipt proves:

- exact target, tokenizer, template, generation, and source identities;
- all five held-out approvals;
- prompt UUID uniqueness and normalized-content uniqueness;
- per-record source and license provenance;
- valid assistant/tool transactions;
- exact row and assistant-loss-token counts per lane;
- the 10,240, 256M, 1B, and 4B view digests that exist;
- no padding, cycling, hidden redistribution, or unreported repeat exposure.

Existing immutable namespaces are never overwritten. Failed or incomplete
artifacts cannot be adopted without a matching input receipt and full replay.

## Failure handling

The pipeline fails closed when any of the following occurs:

- a source revision, file, row schema, license, or approved-use identity is
  absent or changed;
- a held-out or historical-control receipt is unavailable;
- a target, tokenizer, template, special token, or reasoning mode differs;
- an agentic call is malformed, undeclared, unresolved, or paired with the
  wrong recorded result;
- a lane cannot meet its exact token quota;
- a training run restores historical drafter or optimizer state;
- a node, GPU, runtime image, source tree, cache placement, or output identity
  differs from the contract;
- target-output equivalence, checkpoint reload, or evaluator completion fails.

Capacity shortfalls produce signed blocker receipts with eligible rows,
assistant tokens, rejection counts, and limiting sources. They never trigger
cross-domain redistribution or a smaller silently substituted experiment.

## Verification strategy

Implementation follows TDD and must prove:

- prompt UUIDs are independent of regenerated assistant answers;
- held-out variants and derived records are rejected;
- JSON-string and object tool arguments canonicalize identically;
- divergent non-executable agentic actions are rejected;
- exact 10,240-row and 256M/1B/4B token arithmetic;
- `N1` and `N4` expand beyond 1.3M when token capacity requires it;
- source order changes do not change selected bytes;
- all methods start without a drafter checkpoint or trainer state;
- DFlash2 convolution is a numerical identity at initialization;
- FlexAttention uses a node-local Triton cache;
- full comparison inputs differ only in the declared corpus or architecture
  dimension;
- immutable publication and replay are byte deterministic.

CPU tests cover policy, identity, schema, arithmetic, manifest, and command
construction. GPU tests cover real forward/backward, FlexAttention, DFlash2
initialization, checkpoint/export reload, and target-output equivalence. Live
GB200 probes cover the exact 1-node, 2-node, and 16-node Slurm/Pyxis/runtime
boundaries before scientific training.

## Completion criteria

The study is complete only when:

1. every source and held-out catalog is independently approved;
2. `H-native`, `H-synth`, and `M-synth` have immutable 256M and 1B views;
3. the DFlash corpus-ablation runs and paired 1B report are complete;
4. DFlash, DSpark, and DFlash2 have from-scratch runs on the selected corpus at
   matched exposure;
5. every checkpoint exports, reloads, serves, and preserves exact target
   outputs;
6. the final report contains domain acceptance, retention, and GB200 rollout
   throughput with complete provenance;
7. no result is described as equivalent to NVIDIA's published 66B-token
   training run unless that exposure and all associated evidence are actually
   reproduced.
